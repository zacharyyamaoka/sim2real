Camera types: RGB, RGBD and hyperspectral as kits you assign

sim2real main 4c5115d (cards barrier cce0862 first) · 2026-11-11 · every number below is re-run by docs/build_report_camera_types.py from the hidden-truth scenarios tests/test_camera_types.py holds

Name a camera's type and it gets its model ladder, identify routines, configure routines and fidelity metrics. Every identify routine recovers a camera whose true parameters the fit never sees, and its held-out fidelity is within 1.5× the camera's own floor, while the datasheet model fails the same metric (red bars below). Proven in simulation only: no real camera has run these fits yet; the RGB/RGBD exposure lock is the one routine already run on the rack's D435.

The card records (time, equipment, cost, status, alternatives) are in sim2real.cards; tests/test_camera_types.py holds every rung key, parameter name and routine id here to the card. Three routines are honestly not implemented: the D400's on-chip self-calibration, the depth module's emitter/laser search and lens focus (no C-mount camera on Linux yet).

How good is a camera model? The black-box metrics

One rule for every type, the servo's: model error on held-out captures ÷ the real camera against itself; twinned at ≤ 1.5×. The floor is a session floor, σ·√(1/ncalibration + 1/nheld-out): how far a second real calibration session would land from the same held-out capture. A second check: the model's stated noise is right, std(residual ÷ predicted σ) ≈ 1.
