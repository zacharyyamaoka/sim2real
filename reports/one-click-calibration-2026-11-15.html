One-click calibration: where it stands

.calibrate() is already one call — in simulation. On real hardware it isn't wired: on="real" still raises. The pieces that would make it turnkey each run on their own, mostly not yet together.

  • Sim: ur_wrist_test_rig().calibrate(on="sim") plans 6 routines, recovers 22/22 hidden values and passes 3/3 gates (tool p95 0.046 mm) in 29 min, on sim2real main. The pendulum ran end to end on 11-11; the five-bar recovers 20–22 of its 22 values but fails the tool gate, on an unmerged lane.
  • Real: PID tuna, homing, RobotDx's reset ladder and the rack's gate scoring all run on hardware — none is called by calibrate(). The real tool already stops within 1 mm (wrist 98/98, READY 14/14); the real twins don't pass yet (wrist CAN 15 at 2.98× its floor).

The gap to one real click

In the order I'd close it. The first item is the only seam between “works in sim” and “works on the rack”; the rest make it turnkey.

  1. Wire calibrate(on="real") · the one missing seam
    The collect/fit split already exists, so this is a real backend that plays each planned routine's runs() through the rack runner (rackq submissions, bus lock, torque caps) and hands back robot_msgs trajectories for the same fit(). The error message in twin.py already names the path. First target: one pendulum station — today's critical path.
  2. Make the pendulum example load anywhere · found today
    sim2real.examples.pendulum_can11() needs bam_rack_twin's venv: in sim2real's own env it dies with ModuleNotFoundError: bam_rack_twin (I hit it running plan() this morning; the wrist loads fine), and its run still returns no sim2real.calibration/1 record. A one-click that needs the right venv isn't one yet.
  3. PID tuna as a tune routine · PEP 0001 already allows it
    pidtuna's tune(servo, plant, goal) has the right shape; registering it in the catalog lets the planner put it after the fits it needs (friction, inertia, delay).
  4. RobotDx as configure step 0 · inventory vs description
    Turn RobotDx's device tree into a check the planner runs first: every board the description names answers, nothing extra, no faults — or the reset ladder runs before calibration starts.
  5. robot_description from CAD, and the write-back · the two ends
    to_robot_twin() / from_robot_twin() and the Robot Parts type mapping, so the click starts at your CAD and ends back in it.
  6. Real twins inside 1.5× their floor · the hard part
    Real calibrate will expose what the rack scripts already show: wrist CAN 15 at 2.98×, five-bar 1.83–2.57×. The levers named so far are cogging, a rest-state stiction model and direction-dependent ripple.
  7. Land the stragglers · branches
    one-click-fivebar (tool gate 1.18 mm), kincal-bench-1114, hand-eye-method-1113, the motor-models branch and 1dof-rack-sim-to-real all sit unmerged.

Why the AI crushes digital and stalls on real

It isn't intelligence — it's the loop

In code the agent gets an exact, instant, free signal it can repeat a thousand times. On the rack every signal is slow (minutes), costly (arm time is earned), noisy (the wrist's repeat floor is 0.09–0.24°), partly hidden and sometimes destructive (a trip, a wedged fdcanusb that needs a 5 V cut).

This week's surprises were all hidden state: the C1 5 Hz ring was our own host relay (1.143° → 0.011° once off), the printed L2 was 1.5 % short with a 16 mm crank hub, and a 5.7 mm first-grasp offset is still unexplained. Each cost a night because nothing measured it first.

So turnkey = make the real loop look digital

Observable — RobotDx says what's plugged in and healthy. Recoverable without you — the reset ladder and return-to-home. Predictable — a twin inside 1.5× its floor, so most iterations run in sim or the cloud. Graded by a ruler that can fail — sealed truths, held out from another day.

That is exactly the stack above. The button is about twenty lines once on="real" exists — don't build the GUI first.

Wider view 1: zero clicks, not one

A deployed robot shouldn't wait for a click. The same routines can re-run themselves when drift shows — PEP 0012's drift-only T10 routine and the lifelong-sysid branch are the start. One click is the commissioning case; zero clicks is the fleet case.

Wider view 2: CAD isn't the truth, and “plug in” needs a kit

Your CAD was off by a crank hub and 1.5 % on a link, so step one is “as-built” (the ArUco bundle-adjust routines already exist as a type), not “load CAD”. And some routines need equipment — markers, a camera, a pendulum weight. The planner already prices operator time and equipment $, so the click can say “attach the 10:1 pendulum” before it starts.
