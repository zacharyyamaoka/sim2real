# Decision: sim2real tracks every type and deployment in ONE W&B project, sliced by config (2026-11-11)

**Status:** accepted as the default (proposal B). Zach asked for a W&B tracker and three proposals for it on 2026-11-11, with the worry
in his words: "Should we have one weights and biases project per generic type? This could be a lot of projects. But I guess for each one
it's a bit unique, no? OK, having it in one location could work, if we can filter that data to show it for particular types of models or
something…". Overrule it by pointing `sim2real.tracking.wandb_log.PROJECT` (or a `project=` argument) elsewhere; nothing else changes.

## Context

- Every node of a calibration's tree (deployment → arm → joint → tool) answers the same five questions (Floor → Data → Routines → Twin →
  Job, proposal C); a parent passes a question only if it does at its own output and every child does.
- W&B workspaces cannot hold runs from two projects (only reports can), and its permissions are per project.
- The full comparison, weighted criteria first, is section 3 of `docs/KPIS_GATES_CURRICULUM.md`: one project 89 / 100, one per
  deployment 61, one per generic type 46.

## Decision

- **One project, `Sim2Real`, in the entity `zach-yamaoka-independent`.**
- **A W&B run is one node at one twin iteration of one evaluation**, never a rig run (rig runs stay in the archive, the result page and
  Rerun). Each run's config carries its slice keys: `type` (a sim2real type id from `cards/domain_v3.json`), `type_group`, `level`,
  `deployment`, `instance`, `can_id`, `twin_iteration`, `stage_role`, `floor_kind`, `gains`, `evaluation`, `evaluation_state`.
- **An evaluation is identified by its content** (a digest of the result's shown tables): the same numbers resume the same runs, new
  numbers make new runs and mark the older ones `superseded`. Nothing is deleted. Logging refuses a dirty `src/` unless told otherwise.
- **Slices are views, not projects:** one saved view and one report per type and per deployment present, plus an overview, generated by
  `build_views` from the runs and updated in place (`src/sim2real/tracking/wandb_views.json`).

## Consequences

- A new type or deployment is a new config value; rerunning `--views` gives it its view and report.
- A customer cell that must be shared on its own gets `log(result, project="<customer> cell")`: per-deployment isolation for that one
  cell, everything else stays here.
- If one type's media (camera frames, hyperspectral cubes) ever swamps the shared workspace, that media moves to a project of its own;
  its verdicts stay here.
- Do not re-split by type to "clean up" the workspace: the per-type saved views already show one type alone, and a split would scatter
  each rig's tree, so the roll-up could no longer be seen in any one place.
